## 一、总览：安卓现在有哪些能力

| 能力 | 安卓实现 | 鸿蒙现状（我读代码看到的） |
|---|---|---|
| 页面离线壳（断网能打开页面） | **网页侧** `sw.js` 负责，原生**刻意不碰** | 同样由网页负责；需确认 ArkWeb 的 Service Worker 支持情况 |
| `/api` 离线数据（断网能看数据） | `sync/OfflineApi.kt` + `data/OfflineCache.kt` | **没有**（只有同步结果的活动缓存 `Store`） |
| 桌面卡片 | 两个：「今日活动」+「课表」（含进行中进度条） | 一个：「今日活动」（`widget/WidgetUpdater.ets` 读活动缓存）|
| 卡片换天 | 本机零点 `AlarmManager` 闹钟刷新 | 需确认（`updatePeriodMillis` 之类够不够） |
| 活动到点提醒 | `AlarmManager.setWindow` + 通知 | 已有：`remind/ReminderService.ets`（`reminderAgentManager`，日历型提醒） |
| 课程提醒 | 有（提前量 / 开课时 / 7 天滚动窗口） | **没有** |
| 后台常驻（App 没打开也能及时收通知） | 前台服务（`specialUse`）+ 深 Doze 兜底闹钟 | **没有**；`workScheduler` 周期下限 **30 分钟**（`Constants.ets` 里已注明） |

## 二、逐项说明（安卓侧）

### 1. 离线能力：页面壳归网页，原生只做 `/api`

**这一块踩过一个很贵的坑，值得完整抄过去。**

现象：真机上「杀进程重开后断网」，除了主页，点其它标签页全是「网页无法打开」。

根因链条（都在网页侧）：

1. 站点在 Cloudflare Pages 上，会把 `/notices.html` **308 跳转**到去扩展名的 `/notices`；
2. `sw.js` 的预热清单写的是 `.html` 写法，`cache.add()` 跟着跳转取回来的响应带上了 `redirected` 标记；
3. 规范禁止用「跟过跳转的响应」应答**导航请求**（页面与 iframe 的加载都算导航）——浏览器直接判成网络错误；
4. 所以 `/` 能开（它不跳转），而每个 iframe 请求的都是 `xxx.html`，全打不开。

修法（`web/sw.js`）：预热清单改用规范地址、缓存键统一归到规范地址、落盘前去掉 `redirected` 标记、离线回退时按规范地址再找一次（页面里 iframe 与后端下发的 `forms.html` 链接仍是 `.html` 写法，要兼容），缓存名提到 `ca-shell-v2`。

**顺带删掉了安卓原生的「离线壳」**：我们一度以为原生层该兜住页面，照着 `sw.js` 的清单做了一套（`SHELL_PATHS` / `warmShell`）。实测证明它**永远走不到** —— 在 App 里，页面的导航请求会被 Service Worker 先接走，`shouldInterceptRequest` 根本看不见它们。

**给鸿蒙的结论**：**页面壳只该有一处实现**。鸿蒙这边如果 ArkWeb 支持 SW，就让它支持；不要在两处各做一套，否则其中一套是死代码，且会掩盖真正的 bug。

**`/api` 那半边（安卓确实需要原生做）**，要点：

- 按 **URL（含查询串）** 存响应，断网原样回放；
- 单条详情（`/api/notices/123`）不单独缓存 —— 从缓存过的**列表**里按 id 拼回来（后端列表项与详情返回同一行数据，字段一个不少），否则文件数随「点开过多少条」无限涨；
- **写操作**（POST/PUT/DELETE）一律不接管，断网就该失败；
- 服务端**答了**（401 / 500 / `success:false`）时原样透传，**绝不退回缓存** —— 否则「登录态失效了」会被一份旧数据盖住；
- 断网回放**不看 token**：读的是本机已存下的数据，登录态在不在都不影响；
- 后台同步按一份 `PREWARM` 清单，把**网页真正请求的那几个 URL** 也预热一遍，于是离线数据的新鲜度跟着后台同步走，而不是「上次打开那个页面时」；
- 退出登录时连同缓存一起清（否则换账号后断网能翻到上一个账号的通知与课表）。

### 2. 桌面卡片

安卓两个卡片：

- **今日活动**：今天还有活动就显示今天，否则显示下一个有活动的日子；
- **课表**：每条课是**一条浅靛蓝圆角条**（不是几行裸文字）；**正在上的那节用进度条盖出「上到一半」**、文字换成强调色，已上完的整条变灰；今天课上完/今天没课 → 往前找**下一个真有课的日子**并在标题里标出来（「明日课程」/「周五 10-09 课程」），跳过周末与单双周没课的日子；没绑教务时说的是「还没同步到课表」而不是「今日无课」。

两个实现细节值得抄：

- **`RemoteViews` 画不了任意宽度** → 「上到一半」是用 `ProgressBar` 的 `level`（`progressDrawable` 里放 `<clip>`）实现的；另外框架的 `progressBarStyleHorizontal` 会把高度夹在 16dip，必须显式覆盖 `minHeight` / `maxHeight`。
  （鸿蒙的卡片是 ArkTS，可以直接画，不受这个限制 —— 这里只是提一下安卓为什么长这样。）
- **卡片换天**：两个卡片的标题都是「今日 / 明日」，而原来的刷新时机只有「同步成功」+ `updatePeriodMillis`（系统夹到最少 30 分钟）。过了零点没人叫它们，桌面就一直挂着昨天那一屏。现在按**本机零点**排一个 `AlarmManager.RTC` 闹钟（不唤醒设备，睡着就等醒来再刷）专门刷卡片，接收方刷完自己再排下一次；系统时间/时区变更、覆盖安装、打开 App 时各补一次。**`DATE_CHANGED` 特意没有注册** —— 它不在系统的隐式广播豁免名单里，清单注册的接收器收不到。

### 3. 课程提醒

- 按本地课表（不联网）在上课前提醒；「个人中心 → 偏好设置 → 课程提醒」可设提前多久（不提醒 / 5~60 分钟，默认 15）与**是否在开课时再提醒一次**（默认开）；
- 设置存本机，网页经 `CAHost` 桥读写，**改完立刻重排闹钟**（不重排的话要等下次后台同步，用户会以为没保存上）；
- 只排**未来 7 天**，滚动窗口靠「每轮同步后 + 用户改设置后」两处调用不断往前推；
- 闹钟编号按「**绝对日期 + 课程序号 + 类型**」——用「今天往后第几天」的话，同一个闹钟每过一天就换号，天天被当成新闹钟取消重排；
- 课程提醒**单独一条通知渠道**，可以和班级活动/通知分开静音；
- 跨零点下课也要算对（23:00→00:30 是 90 分钟），日期逻辑有单测钉着（`CourseScheduleTest`，17 条）。

### 4. 后台常驻（本轮重点）

**问题**：App 没打开、或手机放着不动一段时间后，收不到通知。

**诊断**（两条病因，机制不同）：

| 通知类型 | 机制 | 为什么会漏 |
|---|---|---|
| 到点提醒（活动开始前 / 上课前） | `AlarmManager`，系统到点拉起进程投递广播 | 本该与 App 状态无关，漏了就是被系统/ROM 的后台限制掐了 |
| 内容提醒（有人发了新通知 / 新活动 / 待填表单） | 每 15 分钟轮询一次，比对基线后弹通知 | **必须有人去拉**。进程没了就没人拉；进 Doze 后 15 分钟会被推到维护窗口（可能几小时） |

这也是「只有刚用过 App 的时候才收得到」的成因：刚用过 → 应用在 ACTIVE 桶、任务跑得勤；放着不动 → Doze 把网络和任务一起压住。

**解法：两条腿，缺一条都不成立。**

- **B：前台服务**（`sync/BackgroundSyncService.kt`）把进程钉住，每 **3 分钟**跑一轮同步；
- **A：免电池优化白名单**（用户点一下）让 **Doze 期间还能联网** —— **前台服务买不到这一条**，它只买得到「进程活着」。

具体要点：

- **服务类型按版本分支传**：API 34+ 用 `specialUse`、29–33 用 `dataSync`、更老不传类型。选 `specialUse` 有两个原因：`dataSync` 在 `targetSdk ≥ 35` 时**24 小时只能累计跑 6 小时**（与常驻冲突），而且 `BOOT_COMPLETED` **不能**启动 `dataSync`（禁启名单里有它，`specialUse` 不在）。
- **服务那一轮只拉核心 3 个接口**（`SyncRunner.run(deep=false)`）：完整一轮是 8 个接口（含离线预热 5 个），按 3 分钟算就是**每人每天约 3840 次**请求 —— 一个班几十号人能把 Cloudflare 免费额度（10 万/天）啃穿，而额度一破是所有人一起用不了。拆开后是 1440 次/人/天，预热仍归 15 分钟那一路。
- **同步逻辑抽成 `SyncRunner`**，15 分钟的 `SyncWorker` 与前台服务共用同一份（含「首轮只记基线、不把历史内容补推一遍」的去重 —— 这条是**刷屏的唯一防线**，抽成纯函数 `pickFresh` 并补了单测）。
- **状态栏会挂一条最低重要级的常驻通知**（系统对前台服务的硬性要求，不能真静默），点它回通知页；个人中心给「后台常驻」开关，关掉只是退回 15 分钟、功能不消失。
- **开机自己起来**走 `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED`（都是后台启动前台服务的合法豁免时机）；`START_STICKY` 只对「进程被内存回收」有效 —— **从最近任务划掉是强停，谁都救不回来**，得再打开一次。
- **深 Doze 兜底闹钟**：前台服务保得住进程、**保不住 CPU** —— 深 Doze 会把 CPU 一起挂起，服务里那个进程内的定时器叫不醒它（真机实测：`force-idle` 期间一轮都没跑，服务本身还活着）。所以另排一个 `AlarmManager.setAndAllowWhileIdle`（Doze 下允许触发、被系统限流到约 9 分钟一次），由广播接收器直接跑一轮同步（接收器不需要前台服务，绕开「Android 12+ 禁止后台启动前台服务」这条）；接收器**只在 `isDeviceIdleMode` 时才真干活**，Doze 外定时器是准的、它不插一脚。
- **个人中心那张「后台通知」卡片**如实显示三项本机状态（有没有免电池优化 / 前台服务在不在跑 / 系统给的待机档），并给两个入口（申请免电池优化、跳 ROM 的「自启动 / 后台管理」页）。

## 三、平台无关的硬约束（AOSP 层的结论，鸿蒙侧要逐条找对应）

| 约束 | 内容 | 安卓侧的处置 |
|---|---|---|
| 后台周期任务下限 | `JobScheduler` / `WorkManager` 的周期下限是 **15 分钟**，Doze 下还会被推迟到维护窗口 | 想要更及时只有两个出口：**前台服务**或**推送** |
| Doze 挂起网络 | 屏幕关 + 静止一段时间后，系统**挂起网络访问**；**前台服务不豁免这一点**，白名单才是唯一确定的豁免 | 所以「A 与 B 必须配套」 |
| 深 Doze 挂起 CPU | 深 Doze 期间 CPU 一起睡，进程内的定时器（`Handler` / 线程池）**不会触发** | 需要 `setAndAllowWhileIdle` 这类「能唤醒设备」的原生机制 |
| 后台启动前台服务受限 | Android 12+ 禁止从后台启动前台服务；豁免名单里有 `BOOT_COMPLETED`、`MY_PACKAGE_REPLACED`、**精确闹钟**、高优先级 FCM 等；**不精确的闹钟不在名单里** | 所以兜底闹钟走「广播接收器直接跑」，不去拉服务 |
| 前台服务必须可见通知 | 系统硬要求，做不出真正静默的常驻 | 用最低重要级 + 文案说明，并给用户开关 |
| 厂商自启动没有标准 API | ROM 自己加的「自启动 / 后台管理」读不到 | 只给「去设置」入口，页面上如实说明读不到，**不猜一个值显示给用户** |

**请鸿蒙侧确认对应概念**（我不熟 ArkTS/鸿蒙的细节，以下都是「要查证」而不是结论）：

1. `workScheduler` 的周期下限（`Constants.ets` 里写的是 30 分钟）——有没有更快的合法路径？
2. 有没有 `continuousTask` 那样的长时任务机制？需要什么权限、`module.json5` 怎么声明、系统是否强制要求挂通知、有没有时长上限？
3. 系统的省电/应用启动管理（类似 MIUI 的自启动）是否有可读的状态查询 API？没有的话按「只给入口、如实说明」处理。
4. 有没有「能唤醒设备」的定时机制（类似 `setAndAllowWhileIdle`），以及它在系统省电模式下是否仍会投递？
5. `ArkWeb` 是否支持 Service Worker（决定离线壳能不能照搬网页那套）。
6. 华为推送（Push Kit）是否可用、是否值得 —— 这是**唯一不依赖 App 存活**的通道；安卓侧我们**刻意没做**（国内网络下 FCM 不可靠），但鸿蒙有自己的推送体系，值得单独评估。

## 四、已知问题与未决项（安卓侧当前状态）

1. **深 Doze 兜底闹钟没查清**：不在 Doze 时投递正常；`dumpsys deviceidle force-idle` 造出来的人为深 Doze 下，闹钟排上了却**凭空消失**（零日志、无续排、Alarm Stats 里也没有我们的 uid，全程 `logcat *:V` 落盘）。怀疑是 `force-idle` 这个人为状态的特性，但**没有证据**。已加两处加固（接收器入口无条件打日志、每次 `onStartCommand` 都续排）。下一步要拿**自然进 Doze** 复验 —— 注意 **USB 充电会阻止自然进 Doze**，所以要么走 adb over Wi-Fi，要么人工关屏放置后再看日志。
2. **从最近任务划掉 App** 之后谁都救不回来（应用进入 stopped 状态），必须再打开一次。这条绕不过去，除非上推送通道。
3. **厂商自启动状态读不到**，只能引导用户去设置里自己找。
4. **请求量预算**：轮询间隔要按「每人每天几次」算一遍再定。3 分钟 × 3 接口 = 1440 次/人/天，几十人的班仍在 Cloudflare 免费额度（10 万/天）内；**不要按 8 个接口算**。
5. 网页侧还有一个既有问题：域名上的 **Browser Cache TTL = 4 小时**会把 `/assets/*`、`/sw.js` 的 `Cache-Control` 改写成 `max-age=14400`（`_headers` 挡不住）。`app.js` 里已用 `updateViaCache:'none'` 保住 SW 更新这条路，但 `/assets/*` 仍可能旧 4 小时（「新页面结构 + 旧样式」）。

## 五、验收清单（安卓是这么验的，鸿蒙照做一遍）

1. `dumpsys` 确认服务在跑、类型正确、常驻通知挂着；点它能否回到通知页
2. 连续几轮的时间戳，确认轮询间隔与设定一致
3. 个人中心那张卡片三项状态是否如实（对照 `dumpsys deviceidle whitelist` / `am get-standby-bucket`）
4. 开关关掉 → 服务与通知一起消失；再打开 → 服务回来
5. 厂商/系统设置入口是否真的能跳过去
6. **端到端**：让同学（或自己往库里插一条只点名本人的）发一条真通知，看几分钟内是否弹出 —— 安卓这次是 04:05:39 插入、04:10:19 前弹出（`id=100007`、渠道 `class_notice_v2`、重要性 HIGH）
7. 划掉任务卡片 → 等 10 分钟 → 记录现象（**大概率被杀，这是 ROM 边界、不是 bug**）
8. 重启手机 → 服务是否自动挂上
9. 关屏静置一段时间 → 轮询是否继续（安卓在人为深 Doze 下**断了**，见第四节第 1 条）

### 验的时候别踩这三个坑

- **`am force-stop`（强停应用）会连它的通知一起清掉** —— 我差点把「测试通知没弹」误判成 bug，实际它弹过了、被我随后的强停清掉了。
- **`adb install -r` 覆盖升级要求签名一致**；debug 包与线上包签名不同，只能卸载重装（会清掉登录态与缓存）。安卓这边是让 CI 出正式签名包再覆盖装的。
- **`force-idle` 不是自然 Doze**。它是 adb 强制的 IDLE，用来验「机制在不在」可以，但结论不能直接外推到真机日常。

## 六、给鸿蒙的优先级建议

1. **课程提醒**（缺功能，且**不依赖任何保活** —— 用 `reminderAgentManager` 就能做，和现有活动提醒同一套）
2. **课表卡片**（缺功能，纯读取同步结果，风险低）
3. **`/api` 离线缓存**（缺功能，纯本地逻辑，能显著改善「没网打不开」的观感）
4. **后台常驻**（最难，建议放到最后，先定「要不要上推送」这个方向）
5. 卡片换天的刷新时机（小，但用户天天能碰到）
